## 2. 왜 이런 일이 생겼나 (근본 원인)

Open-Meteo Geocoding은 GeoNames 기반이다. GeoNames의 **주 색인은 로마자(ASCII) 표기**이고, 한글 표기는 일부 레코드에만 alternate name으로 달려 있다. 그 결과:

1. `language=ko`는 **결과 라벨을 한국어로 번역**해줄 뿐, **한글로 검색되게 해주지 않는다.**
2. 한글 질의가 매칭되는 레코드는 "한글 alternate name을 가진 소수 레코드" = 주로 **행정구역이 아닌 마을·고개·자연지명**과 **북한 지명**.
3. 그래서 대도시는 0건, 대신 동명의 시골 마을과 북한이 올라온다.
4. 게다가 `countryCode` 필터가 없어 북한(KP)이 그대로 노출된다.

즉 이건 "가끔 안 되는 버그"가 아니라 **한글 입력 경로 전체가 잘못된 색인을 때리고 있는 구조적 결함**이다.

### S1. 한글 → 로마자 자동 재질의 (최우선)

현재 fallback 체인은 `ko` → 별칭(해외 전용) → `en`인데, `en` 재시도에도 **한글 원문 그대로** 넘긴다. 그래서 여전히 0건이다.
→ **한글 질의를 로마자로 변환해서 다시 던진다.**

```js
// 1) 국내 주요 지명은 사전 우선 (정확도 100%)
const KR_ROMAN = {
  서울:"Seoul", 부산:"Busan", 인천:"Incheon", 대구:"Daegu", 대전:"Daejeon",
  광주:"Gwangju", 울산:"Ulsan", 세종:"Sejong", 제주:"Jeju", 서귀포:"Seogwipo",
  강릉:"Gangneung", 속초:"Sokcho", 양양:"Yangyang", 평창:"Pyeongchang",
  경주:"Gyeongju", 전주:"Jeonju", 여수:"Yeosu", 순천:"Suncheon", 통영:"Tongyeong",
  거제:"Geoje", 안동:"Andong", 남해:"Namhae", 태안:"Taean", 가평:"Gapyeong",
  춘천:"Chuncheon", 부여:"Buyeo", 공주:"Gongju", 목포:"Mokpo", 포항:"Pohang",
  설악산:"Seoraksan", 지리산:"Jirisan", 한라산:"Hallasan", 북한산:"Bukhansan",
};
// 2) 사전에 없으면 한글 음절 → 로마자 변환기(경량 라이브러리 또는 자체 표)로 폴백

async function searchCity(q) {
  const tries = [
    [q, "ko"],
    [KR_ROMAN[q.trim()] ?? romanize(q), "en"],   // ← 신규
    [resolveAlias(q), "ko"],                      // 해외 별칭 (그랜드캐년 등)
    [q, "en"],
  ];
  for (const [name, lang] of tries) {
    if (!name) continue;
    const r = await geocode(name, lang);
    if (r.length) return renderSuggestions(rank(r));
  }
  renderEmptyState(q);   // "찾지 못했어요 — 영문으로도 검색해보세요"
}
```

효과: 서울·제주·경주·통영 = 0건 → 정상. **13곳 중 3곳 → 13곳 전부.**

### S2. 국가코드 필터 & 북한 차단

```js
function geocode(q, lang, countryCode) {
  const cc = countryCode ? `&countryCode=${countryCode}` : "";
  return fetch(`https://geocoding-api.open-meteo.com/v1/search?name=${encodeURIComponent(q)}&count=10&language=${lang}${cc}&format=json`);
}
// 후처리: 여행 불가 지역 제외
const BLOCKED_CC = new Set(["KP"]);   // 북한
results = results.filter(r => !BLOCKED_CC.has(r.country_code));
```

한글 질의는 국내 의도일 확률이 높으므로 `countryCode=KR`을 우선 시도하는 것도 유효하다.
"강릉 → 황해북도", "전주 → 평안북도", "대구 → KP" 세 건이 즉시 사라진다.

### S3. 결과 랭킹 재정렬

Open-Meteo는 관련도 순 정렬이 약하다. 응답의 `population`, `feature_code`를 이용해 재정렬한다.

```js
const RANK = { PPLC:0, PPLA:1, PPLA2:2, PPLA3:3, PPL:5, MT:4, PRK:4 };  // 수도 > 광역 > 시군 > 마을
function rank(rs) {
  return rs.sort((a,b) =>
    (RANK[a.feature_code] ?? 9) - (RANK[b.feature_code] ?? 9) ||
    (b.population ?? 0) - (a.population ?? 0)
  );
}
```

"부산 → 경상북도 마을", "인천 → 전라남도 마을", "남해 → 대전"이 뒤로 밀리고 광역시가 1순위로 올라온다.

### S4. 국내 목적지 사전 (좌표 내장)

행정구역명이 아닌 **관광 목적지명**은 GeoNames로 잡히지 않거나 부정확하다.
현재 `KOREAN_ALIASES`(해외 36곳)와 같은 방식으로 국내판을 만들되, **문자열 별칭이 아니라 좌표를 직접 내장**해 API 왕복 자체를 없앤다.

```js
const KR_PLACES = {
  "성산일출봉": { name:"성산일출봉", lat:33.458, lon:126.942, admin:"제주 서귀포시", type:"activity" },
  "우도":       { name:"우도",       lat:33.506, lon:126.952, admin:"제주 제주시",  type:"activity" },
  "남해 독일마을":{ name:"독일마을",  lat:34.752, lon:127.958, admin:"경남 남해군",  type:"mixed" },
  "경주 불국사": { name:"불국사",    lat:35.790, lon:129.332, admin:"경북 경주시",  type:"city" },
  "설악산 대청봉":{ name:"대청봉",   lat:38.119, lon:128.465, admin:"강원 속초시",  type:"activity" },
  // 한국관광공사 TourAPI 관광지 데이터로 대량 시딩 가능
};
```

부수 효과: 목적지 유형(도시형/자연·액티비티형)을 **자동 판정**할 수 있어, 페르소나 테스트에서 드러난 "모두 도시형으로 분류됨" 문제도 함께 해결된다.

### S5. 후보 disambiguation UI

지금 자동완성은 `이름 / admin1`만 보여준다. 국내 동명 지명이 많아 오선택이 잦다.
→ **국가 국기 + 광역 + 인구 + (있으면) 유형 배지**를 같이 노출한다.

```
🇰🇷 강릉   강원특별자치도 · 인구 21만 · 해안              ← 1순위
🇰🇷 강릉동 전라남도 · 마을
```

인구 없는 마을 레코드는 시각적으로 즉시 구분된다.

### S6. 기준 도시(출발지) 사용자 지정

`REFERENCE_CITY` 하드코딩을 **출발지 입력**으로 승격한다.

- 입력 필드: "어디서 출발하세요?" (기본값 = 브라우저 로케일/타임존 추정)
- 비교 문구를 동적으로: `"{출발지}의 같은 시기보다 평균 최고기온이 약 N도 낮아요"`
- 인바운드(예: 싱가포르 출발)면 → **"싱가포르보다 평균 최고 24도 낮아요. 지금 옷장에 있는 옷으로는 대응할 수 없는 온도예요."**
  이게 이 서비스가 인바운드 관광객에게 줄 수 있는 **가장 강력한 한 문장**이다.
- 온도차가 15도 이상이면 "겨울옷 자체가 없을 수 있음 → 현지 구매/대여" 안내로 분기.

### S7. 다국어 UI (i18n)

**로마자로는 국내 지명이 100% 검색되는데, UI가 한국어라서 외국인이 그 입력창에 도달하지 못한다.** 이 아이러니가 인바운드 기회 손실의 핵심이다.

- 1단계: `lang.json` 분리 + `navigator.language` 자동 감지 (ko / en)
- 2단계: 추천 아이템명·팁 문구 번역 (OUTFIT_POOLS, CITY_TIPS 대상)
- 3단계: 단위 전환 (°C/°F), 사이즈 표기(한국 사이즈 ↔ US/EU)
- 4단계: 레퍼런스 링크를 Pinterest/Instagram **영문 검색어**로 전환 (`Seoul winter outfit` 등)

투자 대비 효과가 가장 큰 건 1단계 + S6이다. 코드 변경은 국지적이고, 대상 사용자는 완전히 새로 열린다.

### S8. 검색 요청 경합(race) 처리

```js
let searchAbort;
async function searchCity(q) {
  searchAbort?.abort();
  searchAbort = new AbortController();
  const res = await fetch(url, { signal: searchAbort.signal });
  ...
}
```
디바운스(250ms)를 함께 적용한다.

## 4. 실행 로드맵

| 단계 | 범위 | 기대 효과 |
|---|---|---|
| **1차 (즉시)** | S1 + S2 + S8 | 국내 검색 성공률 23% → ~100%, 북한 오인 0건 |
| **2차** | S3 + S5 + S6 | 오선택 감소, 비교 문구가 실제 의미를 가짐 |
| **3차** | S4 + S7 | 관광지명 지원, 인바운드 시장 진입 |

**측정 지표**
- 검색 성공률 = (후보 1건 이상 반환 / 전체 질의)
- 첫 후보 선택률 = (1순위 클릭 / 전체 선택) — 랭킹 품질
- 0건 이탈률 = (0건 후 세션 종료 / 0건 발생)
- 출발지 입력 완료율 (S6 도입 후)

## 5. 이 인사이트가 제품 전략에 주는 함의

버그 수정 이상의 발견이 하나 있다.

> **이 서비스는 이미 인바운드 관광객에게 기술적으로 작동한다. 다만 그들이 들어올 문(언어)이 없을 뿐이다.**

- 국내 여행자에게는 "옷차림 추천"의 가치가 낮다 — 이미 한국 기후를 몸으로 안다.
- 아웃바운드 한국인에게는 유용하지만, 경쟁 대체제(블로그·유튜브·인스타)가 촘촘하다.
- **인바운드 외국인에게는 "체감 불가능한 기온"이라는 진짜 문제가 있다.** 싱가포르·동남아·미국 남부 거주자는 영하를 경험한 적이 없고, 옷장에 대응할 옷이 아예 없다.
- S6(출발지 기준 비교) + S7(영문 UI)만으로 이 시장에 진입할 수 있고, 이때 이 앱의 킬러 기능(과거 10년 실기온을 검색어에 주입)이 가장 크게 작동한다.

→ **다음 버전의 1순위는 "국내 검색 수정"이지만, 그 수정이 열어주는 진짜 기회는 인바운드다.**
