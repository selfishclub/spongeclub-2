## 0. 왜 지금 스키마를 확정하는가

**나중에 스키마를 바꾸면 그 이전 데이터가 날아간다.** 4주 측정 중에 필드를 바꾸면 게이트 판정 자체가 불가능해진다.

그리고 더 중요한 원칙 하나:

> ### 📌 계산해서 얼린다 (compute-and-freeze)
> 9/13에 원본 테이블에서 지표를 그때 계산하지 **않는다.**
> **매주 일요일에 계산해서 `weekly_metrics`에 한 행으로 얼려 넣는다.**
>
> 이유: 중간에 로직이나 스키마가 바뀌어도 **이미 얼린 주는 그대로 남는다.** 판정이 재현 가능해진다.
> 7/10의 실패는 측정을 안 한 것이었고, 그보다 나쁜 실패는 **측정했는데 나중에 해석이 달라지는 것**이다.

## 1. 기록 스키마 — W0에서 이대로 실행

`schema.sql`에 아래를 추가한다. **테이블 4개, 전부 작다.** 기존 `traces`·`daily_focus`는 건드리지 않는다.

```sql
-- ① 사용자 활동 (봇이 메시지를 받을 때마다 upsert)
--    지표1(생존)·지표5(무시율)의 원천
create table user_activity (
  day        date primary key,              -- KST 기준 날짜
  messages   int  not null default 0,       -- 그날 사용자가 봇에 보낸 메시지 수
  last_at    timestamptz
);

-- ② 스튜디오 진입 로그 (P1에서 딥링크 클릭 시 1행)
--    지표4의 원천
create table studio_entry_log (
  id         bigserial primary key,
  entered_at timestamptz not null default now(),
  source     text not null,                 -- 'weekly_report' | 'briefing' | 'direct'
  seed_id    text                           -- 어떤 글감에서 왔나 (없으면 null)
);

-- ③ 발행 기록 (수동 · 텔레그램 한 줄로 입력)
--    지표2의 원천 + 정지선 교정 데이터
create table publication (
  id             bigserial primary key,
  published_at   date not null,
  channel        text not null,             -- 'brunch' | 'linkedin' | 'blog' | 'other'
  draft_fidelity text not null,             -- 'as_is' | 'half' | 'rewrote'  ⭐ 핵심
  corpus_traces  int,                       -- 그때 corpus 크기 (봇이 자동 기입)
  corpus_roles   int,                       -- 걸친 역할 수 (봇이 자동 기입)
  url            text,
  noted_at       timestamptz not null default now()
);

-- ④ 주간 스냅샷 (일요일 23:00 자동 · 한 번 쓰면 절대 수정하지 않는다)
create table weekly_metrics (
  week_start        date primary key,       -- 그 주 월요일 (KST)
  -- 지표 원천
  user_active_days  int not null,           -- 지표1: 그 주 messages>0 인 날 수
  traces_new        int not null,           -- 정지선: 신규 흔적 수
  roles_touched     int not null,           -- 정지선: 걸친 역할 수
  body_traces       int not null,           -- 지표6: '몸' 역할 흔적 수
  seed_candidates   int not null,           -- 지표3: 리포트가 제안한 글감 후보 수
  studio_entries    int not null,           -- 지표4: 스튜디오 진입 횟수
  briefs_sent       int not null,           -- 지표5 분모: 아침 브리핑 발송 건수
  briefs_ignored    int not null,           -- 지표5 분자: 발송 후 24h 무반응 건수
  evening_approved  int not null,           -- 보조: 저녁 승인(숫자 답장) 일수
  computed_at       timestamptz not null default now()
);
```

**구현 위치 (W0 · 1.5h 안에 들어가는 범위)**
| 파일 | 추가할 것 |
|---|---|
| `api/telegram.js` | 인바운드 메시지마다 `user_activity` upsert **1줄** · `발행` 명령 파싱 |
| `api/cron-morning.js` | `briefs_sent` 카운트용 발송 기록 |
| 신규 `api/cron-weekly.js` | 일요일 23:00 → `weekly_metrics` 1행 삽입 + 주간 회고 문안에 지표 4줄 |

## 2. 게이트 지표 6개 — 정의 · 반증 · 스키마

> **경계값에 애매한 구간을 남기지 않는다.** 판정일에 해석 논쟁이 생기면 그 자체가 실패다.

### 지표 ① — 4주 연속 사용 `치명` 🤖 자동

| | |
|---|---|
| **정의** | 마지막 주(**W6: 9/7~9/13**)에 `user_activity.messages > 0` 인 날이 **1일 이상** |
| **통과** | ≥ 1일 |
| **🔴 실패** | **0일** — 마지막 주에 봇에 한 마디도 안 함 |
| **스키마** | `weekly_metrics.user_active_days` (W6 행) |
| **왜 이 정의인가** | *"살아 있다"* 를 발송 여부가 아니라 **사용자 반응**으로 정의한다. 봇은 사용자가 죽어도 계속 보낸다 |

---

### 지표 ② — 4주 안에 실제 글 1편 발행 `치명` ⭐ 🖊️ **수동**

| | |
|---|---|
| **정의** | **2026-08-10 ~ 09-13** 사이 `publication` 행이 **1개 이상** |
| **통과** | ≥ 1편 |
| **🔴 실패** | **0편** |
| **스키마** | `publication` (기록 방법은 §3) |
| **왜 이 기간인가** | P1(본체 연결) 완료가 8/9이므로, 그 다음날부터 센다. 그 이전 발행은 이 시스템의 성과가 아니다 |

> **단일 최중요 지표.** B′("내 것을 밖에 내놓을 형태로 바꾼다")가 작동했다는 유일한 증거다.

---

### 지표 ③ — 주당 발행 가능 재료 `작동` 🤖 자동

| | |
|---|---|
| **정의** | `seed_candidates >= 2` 인 주가 **4주(W3~W6) 중 3주 이상** |
| **통과** | ≥ 3주 |
| **🔴 실패** | ≤ 2주 |
| **스키마** | `weekly_metrics.seed_candidates` |
| **`seed_candidates` 세는 법** | 주간 리포트가 실제로 **문안에 실은** 글감 후보 수. 후보 풀 크기가 아니라 **발송된 개수** |

---

### 지표 ④ — 스튜디오 진입 `작동` 🤖 자동

| | |
|---|---|
| **정의** | `studio_entries >= 1` 인 주가 **4주 중 2주 이상** |
| **통과** | ≥ 2주 |
| **🔴 실패** | ≤ 1주 |
| **스키마** | `weekly_metrics.studio_entries` ← `studio_entry_log` 집계 |
| **주의** | `source='weekly_report'` 만 센다. 직접 URL 진입은 리포트의 성과가 아니다 |

### 지표 ⑤ — 무시율 `작동` 🤖 자동

| | |
|---|---|
| **정의** | `briefs_ignored / briefs_sent` (4주 합계) |
| **"무시"의 정의** | **아침 브리핑 발송 후 24시간 안에 `user_activity.messages` 증가가 0인 날** |
| **통과** | **≤ 0.30** (0.30 포함) |
| **🔴 실패** | **> 0.30** |
| **스키마** | `weekly_metrics.briefs_sent` / `briefs_ignored` |
| **⚠️ 조치가 다르다** | 이 지표의 실패는 **게이트 실패가 아니라 즉시 조치 사유**다 → **빈도 하향**(P7). §4 판정표 참조 |

## 3. 수동 지표 ② 기록법 — 30초 안에 끝나야 한다

**측정이 귀찮으면 안 하게 된다.** 7/10이 그렇게 됐다. 그래서 **사용자가 치는 것은 세 단어**로 줄이고, 나머지는 봇이 채운다.

### 발행 직후 텔레그램에 한 줄

```
발행 브런치 그대로
```

**문법: `발행 <채널> <초안충실도>`**

| 채널 | 초안충실도 | → `draft_fidelity` |
|---|---|---|
| `브런치` · `링크드인` · `블로그` · `기타` | **`그대로`** — 거의 손 안 댐 | `as_is` |
| | **`절반`** — 절반쯤 고침 | `half` |
| | **`갈아엎음`** — 처음부터 다시 씀 | `rewrote` |

### 봇이 자동으로 채우는 것

`published_at`(오늘) · `corpus_traces`(현재 흔적 수) · `corpus_roles`(걸친 역할 수) · `noted_at`

### 봇 응답

```
✅ 기록했어요.
   브런치 · 초안 그대로 · 흔적 23개 / 역할 4개
   URL 있으면 이어서 보내주세요 (안 보내도 돼요)
```

> `url`은 **선택**이다. 필수로 만들면 그 순간 30초를 넘고, 안 하게 된다.

### ⭐ `draft_fidelity`가 왜 핵심인가

**이 한 필드가 P1의 성패를 판정한다.**

| 값 | 의미 |
|---|---|
| `as_is` · `half` | ✅ 출력이 **완제품**이었다. B′가 작동했다 |
| `rewrote` | 🔴 **"완제품"이 거짓이다.** 지표 ②는 통과해도 **P1은 실패**다 — 초안이 백지와 다를 바 없었다는 뜻 |

`corpus_traces` / `corpus_roles`는 [`구현계획.md`](./구현계획.md) §2의 정지선(**흔적 8개 · 역할 3개**, n=1 관측 1회)을 교정할 유일한 데이터다.

## 4. 9/13 게이트 판정표

> **판정 당일에 해석 논쟁이 생기지 않게 미리 못 박는다.** 아래 표를 그대로 읽고 끝낸다.

### 판정 순서

**1단계 — 치명 지표 먼저.** ①②를 본다. 하나라도 실패면 작동 지표를 볼 필요가 없다.
**2단계 — 작동 지표 3개(③④⑤) 중 통과 수를 센다.**
**3단계 — ⑥은 판정에 넣지 않고 경고로만 읽는다.**

| ① 생존 | ② 발행 | ③④⑤ 통과 수 | 판정 | 무엇을 하나 |
|:---:|:---:|:---:|---|---|
| ✅ | ✅ | **3** | 🟢 **통과** | P3 이후 진행. 확장군 인터뷰(P6) 착수 가능 |
| ✅ | ✅ | **2** | 🟡 **조건부 통과** | **실패한 지표 하나만 4주 더 관찰.** 그동안 **새 기능 금지.** 10/11 재판정 |
| ✅ | ✅ | **0~1** | 🔴 **실패 — 출력 문제** | 재료는 나왔는데 안 썼다. **글감 제안 품질**부터 재검. P3 이후 전부 보류 |
| ✅ | ❌ | any | 🔴 **실패 — 최중요 지표** | **B′ 가설 자체를 재검토한다.** 확장군 인터뷰 금지. `01_JTBD검증.md`로 돌아간다 |
| ❌ | any | any | 🔴 **실패 — v1 재현** | 축이 아니라 **습관**의 문제. 전부 접고 원인부터 규명 |

### 별도 규칙 3개

**A. ⑤ 무시율만 실패한 경우 (③④는 통과)**
→ 게이트 **실패로 치지 않는다.** 대신 **즉시 빈도를 낮춘다**(P7 — 하루 2터치 → 1터치). 4주 재관찰 후 재판정.
근거: 무시율은 제품 가설의 실패가 아니라 **개입 총량의 실패**다.

**B. ② 통과했는데 `draft_fidelity = 'rewrote'` 인 경우**
→ 게이트는 통과하되 **P1을 실패로 기록**한다. 다음 4주는 **새 기능 없이 글감 제안 품질만** 손본다.
근거: 발행은 됐지만 이 시스템 때문이 아니다.

**C. ⑥ `몸` = 0 인 경우**
→ 판정과 무관. 다만 **P5 역할 재편의 최우선 항목**으로 올린다.
근거: 1주차에 본인이 중요하다고 지목한 축이 두 번째로 떨어진 것이다.

### 판정일에 할 일 (10분)

1. `select * from weekly_metrics order by week_start;` → 4행 확인
2. `select * from publication where published_at between '2026-08-10' and '2026-09-13';`
3. 위 표에서 해당 행을 찾아 **그대로 읽는다**
4. 결과와 판정을 이 문서 §5에 기록
