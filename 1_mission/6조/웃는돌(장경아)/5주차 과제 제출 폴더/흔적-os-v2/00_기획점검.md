# 흔적 OS — 기획 점검 (Planning Audit)

> PRD 전면 개편에 앞서, **v1이 왜 안 쓰이게 됐는지**를 기록으로 되짚은 문서.
> 근거는 전부 이 저장소에 남아 있는 1~4주차 제출물과 코드다. 추측한 부분은 그렇다고 표시했다.

- 점검일: 2026-07-28
- 점검 대상: 흔적 OS v1.0~v1.2 (`imprint-os-app.vercel.app`)
- 결론 한 줄: **루프를 만들었지만, 루프가 닫히지 않았다. 입금은 자동이고 출금은 수동이었다.**

---

## 1. 지금까지의 궤적

| 주차 | 만든 것 | 지금 상태 |
|---|---|---|
| 1주차 | `보고-포맷-변환` 스킬 (일 영역, 임원 보고 자동화) | 흔적 OS와 **연결되지 않음** |
| 2주차 | 흔적 OS 기획 + 두뇌(스킬) + 텔레그램→Vercel→개인저장소 캡처 파이프 | 캡처만 생존 |
| 3주차 | 실서비스 v1.0 (Next.js·Supabase·Haiku) + v1.1 주간회고 + v1.2 글감스튜디오 + UI 리프레시 | **회고·스튜디오만 생존** |
| 4주차 | 고고버디 (별개 프로젝트, 첫 정식 PRD) | 흔적 OS로 돌아오지 않음 |
| 5주차 | — | 공란 |

**주목할 사실 하나:** 흔적 OS는 3주차에 "완성"으로 선언됐지만, **정식 PRD가 한 번도 없었다.** 2주차의 기획 문단이 전부다. 처음으로 PRD를 쓴 건 흔적 OS가 아니라 4주차 고고버디였다. 즉 이번 작업은 "개편"이라기보다 **처음으로 제대로 된 PRD를 쓰는 일**에 가깝다.

## 2. 원래 명제와 실제로 만들어진 것

> **선언:** "내가 시스템을 돌보는 게 아니라, 시스템이 내 흔적을 돌본다."

**실제 구현된 하루:**

```
흔적이 스쳐감
  → 내가 알아챈다              ← 사람
  → 담을 만한지 판단한다        ← 사람
  → 텔레그램을 연다             ← 사람
  → 한 줄로 요약해 보낸다        ← 사람
  → [서버가 분류·저장한다]        ← 시스템 ✅
  → 내가 "본업 복원"이라고 부른다  ← 사람
  → [서버가 한 화면을 보여준다]    ← 시스템 ✅
```

자동화된 두 칸을 빼면 **나머지 다섯 칸이 전부 사람 몫**이다. "30초 캡처"는 *보내는 시간*을 잰 것이지, **"지금 이걸 보내야 한다"고 판단하는 비용**을 잰 게 아니었다. 그리고 실제로 무너진 곳이 정확히 거기다 — *던지는 것조차 안 하게 됐다.*

## 3. 구조적 결함 5개

### 결함 1 — 입금은 자동, 출금은 수동. 루프가 닫히지 않았다

| 단계 | 자동화 | 상태 |
|---|---|---|
| 캡처 | 텔레그램 → 서버 자동 저장 | ✅ |
| 분류 | Claude 자동 분류 | ✅ |
| **복원** | **내가 "본업 복원"이라고 불러야 함** | ❌ |

2주차 로드맵의 3단계 — *"역할 전환 감지 시 복원 화면 자동 푸시"* — 는 끝내 미완으로 남았다. 그 결과 **가치를 수령하는 유일한 통로가 내 능동적 호출에 묶였다.**

인출이 귀찮으면 입금할 이유가 사라진다. "꺼내볼 이유가 없었다 → 던지지도 않게 됐다"는 순서는 우연이 아니라 구조가 시킨 것이다.

### 결함 2 — 이미 남고 있는 흔적을 줍지 않고, 새 입력을 요구했다

내 흔적은 이미 캘린더·메일·메신저·블로그에 매일 남고 있다. 흔적 OS는 그걸 줍는 대신 **"여기에도 한 번 더 적어라"** 고 요구했다. 기록해야 할 곳이 하나 더 늘어난 셈이다.

"시스템이 내 흔적을 돌본다"는 명제를 문자 그대로 지키려면, 캡처는 **요구가 아니라 수거**여야 했다.

### 결함 3 — 역할 4개가 내 실제 삶과 맞지 않았다

1주차 인터뷰에서 직접 말한 삶의 영역:
> *"수술·병가 후 복귀 초기라 재활 운동·수면(4시간 이상) 리듬 지키기"*

그런데 2주차에 확정한 역할은 **본업 / 콘텐츠 / 사이드 / 엄마** — **몸의 자리가 없다.**

그 결과 2주차 분류 테스트에서 이런 일이 실제로 일어났다:

| 던진 한 줄 | 분류 결과 |
|---|---|
| 아침 재활 운동 15분 루틴 지키기 | **미분류** |

내가 일주일 전에 "지금 내 삶에서 중요하다"고 지목한 것이, 내가 만든 시스템에서 **미분류로 떨어졌다.** 그리고 `미분류`는 설계상 '버리지 않는 보관함'이었지만, 아무도 열지 않는 이상 실질적으로는 무덤이다.

덧붙여 역할은 **고정 스키마**인데 삶은 시기마다 바뀐다. 병가 복귀기·이직기·입시기의 역할 구성은 전부 다르다.

### 결함 4 — 저장은 있는데 '판단'이 없었다

복원 화면의 출력은 이랬다:

```
▶ 지금 열린 루프 (최대 5개)
▶ 최근 생각·글감 (최근 3개)
▶ 한 줄 브리핑
```

이건 **목록**이지 **판단**이 아니다. *"그래서 지금 당장 뭐부터?"* 에 답하지 않는다. 목록을 보고 우선순위를 정하는 일은 여전히 내 몫이었고, 그건 원래 없애려던 그 '재부팅'과 크게 다르지 않다.

**결정적인 아이러니:** 이 문제의 답을 **본인이 이미 4주차에 찾았다.**

> 고고버디 유저 피드백: *"바로 시작할 수 있는 다음 미션을 가장 눈에 띄게"*
> → 반영: **"지금 이거 하나" 카드를 최상단에** (미완료 1순위 + 25분 타이머 + 완료 버튼)
> → 결과: 타깃 유저가 직접 만족을 표한 개선

**다른 프로젝트에서 유저 검증까지 끝낸 해법을, 흔적 OS로 역수입하지 않았다.** v2에서 가장 먼저 가져와야 할 자산이다.

### 결함 5 — 기능은 늘었는데 '쓰는 순간'은 안 늘었다

3주차 하루 동안: v1.0 배포 → v1.1 주간회고 → v1.2 글감스튜디오 → UI 리프레시.

본인도 그날 이미 감지했다:
> *"바이브 코딩은 기대치를 끌어올린다. (…) **선택과 집중이 필요한 시점이다.**"*

만드는 문턱이 낮아지자 만드는 속도가 올라갔지만, **쓰는 문턱은 하나도 안 내려갔다.** 기능 수와 사용률은 무관하다 — v1이 그걸 증명했다.

## 4. 살아남은 것이 알려주는 설계 원칙

이번 점검에서 가장 값진 데이터는 "안 썼다"가 아니라 **"이건 그래도 썼다"** 쪽이다.

| 기능 | 생존 | 왜 |
|---|:---:|---|
| 주간 자동 회고 | ✅ | **내가 안 불러도 먼저 온다** (push) |
| 글감 스튜디오 | ✅ | **부를 이유가 명확한 순간이 있다** (글 쓸 때) + 출력이 완제품(초안) |
| 캡처 | ❌ | 매번 내가 시작해야 함 |
| 분류 | ❌ | 결과를 볼 이유가 없음 |
| 복원 | ❌ | 내가 호출해야 하고, 출력이 목록(재료)일 뿐 |

**생존 조건 두 가지가 선명하다.**

1. **먼저 온다 (Push).** 사용자의 기억력에 의존하지 않는다.
2. **완제품을 준다 (Output ≠ 재료).** 목록이 아니라 "이거 하세요" 또는 "이 초안 쓰세요".

> ### v2 제1원칙
> **사용자가 여는 제품이 아니라, 사용자를 찾아오는 제품.**
> 그리고 찾아왔을 때 재료가 아니라 완제품을 내민다.

## 5. 그 밖에 남은 숙제

**① 프라이버시 (3주차에 지적받고 미뤄둠)**
> *"텔레그램 → Vercel → Anthropic → Supabase 를 내 사적 기록이 통과한다"*

당시 *"조만간 업그레이드 예정"* 으로 남겨졌고 아직 그대로다. 아이 일정·건강 기록처럼 가장 사적인 데이터가 가장 많이 흐르는 구조라, **제품화하려면 이건 선택이 아니라 전제**다.

**② 1주차 재료와의 단절**
1주차 인터뷰가 지목한 "가장 소진되는 지점"은 **보고 포맷 변환(일 영역)** 이었다. 2주차에 흔적 OS로 넘어가면서 그 선이 끊겼고, `보고-포맷-변환` 스킬은 고아가 됐다. v2에서 이걸 **'본업' 역할의 깊이 레이어로 회수할지, 명시적으로 버릴지** 결정이 필요하다. (→ PRD에서 결정)
