# 5주차 — 마지막 과제 🏁

> 이번 기수의 마지막 과제예요. 과정과 소회를 기록해주세요. (다 못 채워도 OK!)

> 소규모 습관 커뮤니티를 매주 운영하는 데 드는 시간을 줄이려고 만든 **내부 운영 도구**입니다.
> Discord에 흩어져 있는 참여 기록을 모아서, "이번 주에 뭘 확인하고 뭘 마감해야 하는지"를
> 한 화면에서 처리하는 게 목표였습니다.

## 🎯 과제 1. 구현, 그 다음의 것

![과제 1 안내](https://github.com/selfishclub/spongeclub-2/raw/main/_meta/week5/mission1.png)

> 만드는 건 끝났는데 — 그 다음이 진짜 시작이에요 (답이 안 나와 있어도 OK, 고민을 꺼내놓는 것 자체가 과제)

- **지금 걸려 있는 고민 하나:**

  > **운영 부담을 줄이려고 만든 도구가, 그 자체로 새로운 운영 부담이 되는 것.**
  > 만드는 건 끝났는데 — "이걸 내가 6개월 뒤에도 매주 열고 있을까?"에 자신 있게 답을 못 하겠습니다.

- **그게 왜 고민인지 (무엇이 걸리는지):**

  **1) 내가 풀려던 문제가 "만들 것이 없어서"가 아니었다**

  원래 문제는 "이번 주에 누가 뭘 했는지 파악하는 데 매주 두어 시간이 든다"는 것이었습니다. 그래서 도구를 만들었는데, 만들고 나니 없던 일이 하나 생겼습니다. 데이터를 최신으로 유지하는 일. 도구는 Discord를 읽어서 보여주는데, Discord 쪽이 바뀌면 도구도 맞춰야 합니다. 파악하는 시간은 줄었는데 맞추는 시간이 새로 생긴 셈이라, 순이득이 얼마인지 아직 모르겠습니다.

  **2) "진짜 기준이 어디냐"가 흐려지는 순간이 제일 무섭다**

  지금은 Discord가 정본(원본, 진짜 기준)이고 도구는 따라 읽기만 합니다. 그런데 도구가 편해지면 자연스럽게 "여기서 바로 고치지 뭐"가 생깁니다. 그 순간 같은 정보가 두 군데에 살게 되고, 둘이 다른 말을 하면 어느 쪽을 믿어야 할지 모르는 상태가 됩니다. 이건 기능 버그보다 훨씬 고치기 어렵습니다. 실제로 이 위험을 코드 차원에서는 막아뒀습니다 — 역할 판정은 Discord 역할 이름만 보고 하고, 도구에서 임의로 못 바꿉니다. 하지만 규칙은 사람이 지키는 것이라, 언제까지 지켜질지는 모릅니다.

  **3) 기능은 더 붙일 수 있는데, 그게 답이 아닌 것 같다**

  지금도 "이거 있으면 편하겠는데" 목록이 계속 나옵니다. 그런데 진짜 필요한 건 기능 추가가 아니라 "이 화면을 안 열어도 되게" 만드는 쪽인 것 같은데, 그건 만드는 재미가 없어서 자꾸 미루게 됩니다. 이 관성이 걸립니다.

  **4) 혼자 쓰는 도구는 피드백이 없다**

  운영자가 저 혼자입니다. 그래서 불편해도 그냥 적응해버립니다. 남이 쓰면 "이거 왜 이래요?"가 나올 텐데, 혼자 쓰면 그 신호가 아예 안 옵니다. 잘 만들었는지 못 만들었는지 판단할 근거가 내 감밖에 없다는 게 제일 불안합니다.

- **어떻게 풀어볼 생각인지:**

  **① 도구를 "쓰는 곳"이 아니라 "읽는 곳"으로 못 박기**
  기록은 원래 하던 곳(Discord)에서 그대로 하고, 도구는 모아서 보여주기 + 마감 처리만 합니다. 즉 도구를 지워도 데이터는 안 없어지는 상태를 유지합니다. → 이러면 최악의 경우에도 "도구를 접는" 선택지가 남습니다. 이게 제일 중요합니다.

  **② 4주간 그냥 써보면서, 한 번도 안 연 화면은 지운다**
  기능 추가가 아니라 삭제를 기본값으로 두려고 합니다. "있으면 좋은데 안 씀"이 쌓이는 게 도구가 죽는 가장 흔한 방식이라고 생각해서요.

  **③ 매주 한 줄만 기록한다: "이번 주에 이 도구가 아껴준 시간"**
  체감이 안 나오는 주가 3주 연속이면 접거나 대폭 줄이는 근거로 씁니다. 만든 게 아까워서 계속 붙잡는 상황을 미리 막아두고 싶습니다.

  **④ 자동화 선은 계속 보수적으로 유지**
  지금 커뮤니티에 글을 올리는 건 반드시 사람이 한 번 확인해야 나갑니다. 편해지자고 만든 도구지만, 잘못 나간 글은 되돌릴 수 없어서 여기는 안 풀 생각입니다. "어디까지 자동화하고 어디부터 사람이 볼 것인가"의 기준을 계속 다듬는 중입니다.

- **필요한 게 있다면 무엇인지:**
  - "관리 도구를 만들었다가 결국 안 쓰게 된" 경험담. 성공 사례보다 이게 훨씬 궁금합니다. 왜 안 쓰게 됐는지, 언제부터 안 열었는지.
  - 혼자 쓰는 도구를 오래 유지하는 분들의 습관. 어떻게 관성을 만드셨는지.
  - 내 화면을 처음 보는 사람의 30초 반응. 나는 이미 다 알고 만들어서 "이게 왜 여기 있지?"가 안 보입니다. 그 시선이 필요합니다.

## 🏁 과제 2. 구현 마무리 + 실제 유저 피드백 받기

![과제 2 안내](https://github.com/selfishclub/spongeclub-2/raw/main/_meta/week5/mission2.png)

> 시작할 때 "이번엔 이건 꼭 만들겠다" 했던 것 — 지금 어디까지 왔나요? (스폰지클럽 내 유저피드백 모집 가능)

- **최종 완성한 것 (지금 어디까지):**

  **시작할 때 하려던 것 vs 지금**

  | | 시작할 때 | 지금 |
  |---|---|---|
  | 목표 | 주간 결과를 이미지 카드로 만들어주는 도구 | **주간 운영 전체를 처리하는 Admin OS** |
  | 데이터 | 가짜(합성) 데이터 | **실제 운영 DB + 실제 Discord** |
  | 상태 | 로컬에서만 동작 | **배포 + 로그인 + 매주 자동 실행** |

  → 중간에 방향을 크게 한 번 틀었습니다. (아래 "어려웠던 점 1번")

  **화면 5개로 정리했습니다.**

  1. **오늘** — 메인 화면. 운영 기간, 누적 주간 기록, 누적 모임 횟수, 현재 멤버 구성, 회고 작성률, 활성 챌린지를 한 화면에 보여주고, 아래에 이번 주 할 일을 둡니다. 누적 숫자는 "지금 등록된 사람" 기준이 아니라 기록 원장을 직접 집계해서, 누가 중간에 나가거나 나중에 들어와도 과거 숫자가 흔들리지 않습니다.
  2. **챌린지** — 초안 → 예정 → 진행 → 완료 → 보관. 이름만 있는 초안 상태로 먼저 만들고 날짜·채널은 나중에 채우며, 시작 버튼을 누를 때 Discord 채널이 진짜 있는지 다시 확인하고 저장합니다.
  3. **동료** — 역할 관리와 Discord 동기화. 한 명은 세 역할 중 하나만 가지며, 역할 판정 기준은 Discord 쪽 역할 이름입니다. 역할이 0개면 미선택, 1개면 확정, 2개 이상이면 "확인 필요"로 표시하고 기존 값을 유지해 애매할 때 도구가 멋대로 하나를 고르지 않게 했습니다.
  4. **원씽모임** — 모임 기록을 초안으로 만들고 확인 후 게시. 공개 링크에서 내용을 불러와 초안 생성 → 운영자가 직접 수정 → 미리보기 → 확인 → 게시하며, 입력이 비어 있으면 그럴듯한 내용을 지어내지 않고 "불확실"로 표시합니다. 웹 화면은 절대 직접 Discord에 글을 쓰지 않고 대기열에 넣기만 하며, 실제 게시는 별도 실행기가 합니다.
  5. **설정 / 감사 로그** — 운영 설정과 모든 변경 이력. 누가 언제 뭘 바꿨는지 남고 CSV로 내보낼 수 있습니다.

  그 밖에 매주 자동 실행(주간 스레드 생성이 정해진 시각에 자동으로 돔)과, 로그인 없이는 아무것도 안 보이는 안전장치가 있습니다.

  **만든 규모**

  | 항목 | 수치 |
  |---|---|
  | 커밋 | 33개 |
  | 코드 | 약 14,800줄 |
  | 테스트 코드 | 약 7,400줄 (테스트 파일 55개) |
  | 테스트 종류 | 단위 / 통합 / 실제 브라우저(E2E) 3단 |

  기술 구성: Next.js 16 · TypeScript(엄격 모드) · Postgres · Discord 봇 · Vercel 배포

  **🔒 안전장치** (실데이터를 다루는 도구라 여기 제일 신경 썼습니다. 원칙은 하나, **애매하면 막는다(fail-closed)**.)
  - 허용 목록에 없으면 거부. 목록을 아예 설정 안 하면 아무도 못 씁니다. (설정을 깜빡한 게 "전체 허용"이 되는 사고를 막으려고 반대로 뒀습니다)
  - 테스트용 우회 플래그는 배포 환경에서 자동 무효화. 실수로 켜져도 안 열립니다.
  - 소속이 확인 안 되는 데이터는 집계에서 제외. 다른 그룹 숫자가 섞이지 않습니다.
  - 외부 게시는 기본 차단. 확인·채널·권한이 전부 갖춰져야만 대기열에 들어갑니다.
  - 오류 원문을 화면에 안 띄웁니다. 토큰이나 내부 주소가 새는 걸 막으려고요.
  - 감사 기록에 신원을 위장하지 않습니다. 로그인 안 한 방문자를 '운영자'로 적지 않습니다.

  **😵 만들면서 어려웠던 점 5가지**

  **1. 방향을 중간에 크게 한 번 틀었습니다 (제일 크게 배운 것)**
  처음 만든 건 "주간 결과를 예쁜 이미지 카드로 만들어주는 도구"였습니다. 잘 만들었고 잘 돌아갔지만, 다 만들고 실제로 써보니 매주 진짜 하는 일은 카드 만들기가 아니라 "이번 주 운영"이었습니다. 카드는 마지막 5분짜리 일이었고, 나머지 시간을 잡아먹는 건 누가 뭘 했는지 파악하고 누가 빠졌는지 확인하고 뭘 마감할지 정하는 부분이었습니다. 그래서 카드 쪽을 접고 정보구조를 전부 다시 짰습니다. 배운 것: 만들기 전에 아무리 고민해도 뭐가 진짜 문제인지는 만들어봐야 알게 됩니다. 대신 "갈아엎을 수 있게" 작게 만들어야 한다는 것도 같이 배웠습니다.

  **2. 가짜 데이터로는 절대 안 보이던 문제들**
  합성 데이터에선 완벽하게 빨랐는데, 실데이터를 붙이자마자 두 가지가 터졌습니다.
  - 사람 수만큼 조회를 반복하고 있었습니다 — 동료 목록 화면이 한 명당 따로따로 DB를 조회 중이었는데, 21명 기준 42회/5,245ms → 한 번에 묶어 조회 2회/409ms로 약 13배 빨라졌고, 이제 인원수와 무관하게 조회 횟수가 고정입니다.
  - 매 화면마다 Discord에 채널 목록을 물어보고 있었습니다 — 화면 한 번 열 때마다 324~453ms를 버리고 있어서 30초 동안만 재사용하도록 바꿨습니다. 단, 실패는 저장하지 않고(Discord가 잠깐 죽었다 살아나면 바로 반영), 저장·시작 같은 중요한 순간엔 재사용본을 안 쓰도록(없는 채널이 통과하는 걸 막기 위해) 이 경계를 테스트로 못 박아뒀습니다.

  배운 것: 성능은 실데이터를 붙여야만 보입니다. 그리고 "빠르게 만들기"보다 "빨라지려다 뚫리는 구멍"을 같이 막는 게 훨씬 어렵습니다.

  **3. 배포하고 나서야 알게 된 것 — 서버가 어디서 도는지**
  처음엔 내 컴퓨터 안의 파일에 데이터를 저장했는데, 배포하니 서버가 매번 새로 뜨면서 데이터가 사라져 원격 DB로 옮겼습니다. 그런데 원격 DB로 옮긴 뒤 챌린지 화면이 300초 동안 멈춰 있다가 강제 종료되는 문제가 생겼습니다. 원인은 DB 연결을 1개만 쓰도록 설정해뒀는데 화면이 세 가지를 동시에 조회하면서 서로 물려 영원히 안 끝나는 교착 상태가 된 것 — 게다가 그 연결은 서버 전체가 공유해서 한 번 막히면 이후 모든 요청이 같이 죽었습니다. 연결 수를 1개→3개(1.9초 완료)를 거쳐 5개로 여유를 확보했고, 같은 일이 다시 안 생기게 테스트로 고정해뒀습니다. 배운 것: "이거 어디서 돌 건데?"를 처음에 정했어야 했습니다. 로컬에서 되는 것과 배포에서 되는 것은 다른 문제입니다.

  **4. DB 구조를 바꾸는 게 제일 무서웠습니다**
  챌린지를 "날짜 없이 초안으로 먼저 만들 수 있게" 바꾸려는데 기존 DB는 날짜가 반드시 있어야 하는 구조였고, 이미 운영 데이터가 들어 있어서 테이블을 그냥 지우고 다시 만들면 연결된 등록·인증 기록·감사 로그가 전부 같이 삭제되는 상황이었습니다. 그래서 연결을 잠시 끊고 → 새 구조로 옮기고 → 다시 잇는 순서로 처리했습니다. 배운 것: 코드는 틀리면 되돌리면 되는데 데이터는 한 번 날아가면 끝입니다. 여기만은 시간을 아끼면 안 됐습니다.

  **5. "어디가 진짜 기준인가"를 정하는 게 코드보다 오래 걸렸습니다**
  Discord와 도구가 서로 다른 말을 하면 누구를 믿어야 할지 안 정하고 만들면 나중에 반드시 꼬입니다. 그래서 "Discord가 정본, 도구는 따라 읽기만 한다"는 규칙을 먼저 못 박았습니다 — 역할은 Discord 역할 이름으로만 판정, 애매하면(2개 이상) 도구가 고르지 않고 "확인 필요"로 남기고 기존 값 유지, 게시는 웹이 직접 하지 않고 실행기에 넘김. 이 세 줄을 정하는 데 든 시간이 실제 코드 짜는 시간보다 길었습니다. 배운 것: 어려운 건 기능이 아니라 경계를 정하는 일이었습니다.
