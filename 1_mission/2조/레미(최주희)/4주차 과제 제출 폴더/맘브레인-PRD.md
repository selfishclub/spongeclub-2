## 1. 개요 (Overview)

### 1.1 한 문장 정의

학교·학원의 온갖 알림 채널에서 온 **캡처·PDF를 던지기만 하면**, AI가 숙제·준비물·행사·수납을 **일자별×기관별로 정리하고 전날 저녁에 리마인드**해주는 워킹맘 전용 서비스.

### 1.2 배경 (Why now, Why me)

- 아이 하나가 다니는 기관은 학교 1곳 + 학원 2~4곳. 각 기관의 공지는 **알림장 앱, 단톡방, 가정통신문 PDF, 종이 알림장** 등 서로 다른 채널로 흩어져 도착한다.
- 워킹맘은 업무 중에 이 채널들을 실시간으로 챙길 수 없다. 결과: **준비물 누락, 숙제 미확인, 수납 기한 놓침** — 그리고 그때마다 따라오는 죄책감.
- 문제의 본질은 "정보가 없다"가 아니라 **"정보가 흩어져 있고, 기억 부담이 전부 엄마의 머릿속에 있다"**는 것.
- 작성자는 1~3주차에 「관점노트 OS」로 *텔레그램 캡처 → AI 분류 → 자동 처리 → 웹 대시보드* 파이프라인을 직접 구축·검증했다. 같은 아키텍처를 **본인이 매일 겪는 육아 운영 문제**에 적용한다.

### 1.3 주요 가치 · 소구 방식

**이 프로덕트가 지키는 것 (한 줄):**

> **"기억은 시스템이, 아이는 엄마가."**
> — 엄마의 인지 자원을 '관리'가 아니라 '아이와의 연결'에 쓰게 한다.

**페르소나의 언어로 번역한 소구 문장:**

> **"알림장은 캡처해서 던져만 두세요. 내일 챙길 건 오늘 저녁 8시에 제가 알려드릴게요."**

단순 일정 관리 앱이 아니다. 맘브레인이 대신 기억하는 이유는 단 하나 — 엄마가 확보한 저녁을 아이에게 쓰게 하는 것. 그래서 행사 리마인드에는 일정만이 아니라 **"아이와 나눌 대화 거리"**가 함께 온다. 이 가치가 기능 취사선택의 기준이다: *기억 부담을 줄이는 기능은 넣고, 관리 부담을 늘리는 기능은 뺀다.*

## 2. 문제 정의 (Problem Statement)

| # | 문제 | 현재의 대응 | 비용 |
|---|------|-------------|------|
| P1 | 알림 채널이 기관마다 달라 정보가 흩어짐 | 퇴근 후 앱·단톡방을 하나씩 역추적 | 매일 저녁 20~30분 + 누락 리스크 |
| P2 | 숙제·준비물을 전날 저녁에야 확인 (또는 당일 아침에 발견) | 머릿속 기억 + 냉장고 메모 | 아침 전쟁, 아이 앞에서의 미안함 |
| P3 | 학교 수납·학원비 납부일이 제각각 (월납·분기납·1회성) | 캘린더에 손으로 옮겨 적음 (자주 빠뜨림) | 연체·독촉 문자, 예상 못 한 지출 |
| P4 | 행사(현장학습·발표회)를 놓치면 일정 문제를 넘어 **아이와의 대화 기회**를 놓침 | 우연히 기억나면 물어봄 | "엄마는 내 일에 관심 없어"라는 신호 |

**핵심 통찰:** 이 모든 문제의 공통 뿌리는 *분산된 입력*과 *엄마 단일 장애점(Single Point of Failure) 기억 구조*다. 입력을 한 곳으로 모으고 기억을 시스템으로 옮기면 네 문제가 동시에 풀린다.

## 3. 타겟 사용자 (Target User)

### 3.1 타겟

**미취학(어린이집·유치원) 및 초등학생 자녀를 둔 풀타임 워킹맘**
(v1 검증은 작성자 본인 = 초등 자녀 케이스로 시작하되, 온보딩·기관 모델은 미취학 기관까지 기본 지원 — 2026-07-24 타겟 확장 반영)

- 아이 기관: 학교 1곳 + 학원 2곳 이상
- 알림 채널 3개 이상을 오가며 정보를 수집 중
- 스마트폰 캡처는 일상적으로 하지만, 캡처 후 정리는 못 하고 있음
- 평일 저녁 시간이 짧고 소중함 — 도구에 쓸 시간은 하루 1분 이하여야 함

### 3.2 페르소나 스냅샷

> **레미, CRM 컨설턴트·디지털마케터, 초등 자녀 1명 (학교 1곳 + 학원 4곳, 알림 채널 4종)**
> 낮에는 고객사 미팅과 캠페인 운영으로 알림장을 볼 틈이 없다. 저녁 9시에야 단톡방을 거슬러 올라가다 "내일 물감 준비"를 발견하고 편의점으로 뛴다. 학원비 이체일은 24일·26일·28일로 제각각이고, 분기 수납은 늘 기습적이다.

**페르소나가 실제로 뱉은 문장:**

> 💬 *"업무를 하다 보면 학교나 학원 알림장의 준비물을 챙기기가 쉽지 않고, 숙제 내역을 체크하는 것 또한 놓칠 때가 많아."*
>
> 💬 *"아이가 '엄마, 나 내일 현장학습 가'라고 말했을 때 처음 알게 되는 게 제일 미안해."*

### 3.3 확장 경로 (v2~v3)

- v2: 아이가 직접 보는 체크보드 (스스로 챙기는 습관 형성)
- v3: 멀티테넌트 — 다른 워킹맘도 가입해 쓰는 서비스 (작성자의 CRM·마케팅 역량으로 검증할 시장)

## 4. 목표와 성공 지표 (Goals & Metrics)

### 4.1 북극성 지표 (North Star)

> **"엄마가 머리로 기억해야 했던 항목 수 = 0"** (주 단위 측정)

### 4.2 v1 완료 기준 (Definition of Done)

1. 실제 알림장 캡처(학교 1곳 + 학원 2곳)를 던지면 → 숙제·준비물·행사·수납이 올바르게 추출·분류된다
2. 매일 저녁 지정 시각에 "내일 챙길 것" 브리핑이 기관별로 묶여 자동 발송된다
3. 수납 D-1 리마인드가 실제로 도착한다
4. 웹 대시보드에서 주간 일정표(날짜×기관)와 이번 달 지출 뷰가 보인다
5. **1주일 실사용 후: 시스템 밖에서 따로 기억한 항목 0건**

### 4.3 보조 지표 (행동 관찰 기반)

"좋아요"가 아니라 **관찰 가능한 행동**으로 잰다:

- **다시 던졌는가** — 첫 사용 후 7일 연속으로 캡처를 던졌다 (습관 형성의 증거)
- **다시 열어봤는가** — 저녁 브리핑 수신 후 대시보드를 열거나 완료 체크를 했다
- **시스템 밖 기억이 사라졌는가** — 냉장고 메모·수기 캘린더 기록이 0건이 됐다
- 캡처 1건당 처리 시간(던지기까지): 30초 이내
- 추출 정확도: 리마인드 항목 중 수정 필요 건수 주 1건 이하
- 아이 대화 카드 실행률: 행사 대비 대화 체크 비율

## 6. 기능 요구사항 (Functional Requirements)

### P0 — 없으면 제품이 아님

| ID | 기능 | 요구사항 |
|----|------|----------|
| F1 | **만능 인박스** | 텔레그램으로 이미지·PDF·텍스트 수신. 어떤 채널의 캡처든 형식 제한 없음. 수신 즉시 "담았어요" 회신 |
| F2 | **AI 추출·분류** | Claude 비전으로 원본에서 추출: ①기관(학교/학원명) ②날짜·기한 ③유형(숙제/준비물/제출물/일정/수납) ④내용 ⑤금액(수납 시). 한 캡처에 여러 항목이 섞여 있으면 개별 분리 |
| F3 | **전날 저녁 브리핑** | 매일 지정 시각(기본 20:00)에 익일 항목을 기관별로 묶어 텔레그램 발송. 반복 항목(매주 수요일 줄넘기 등) 포함 |
| F4 | **수납 리마인드** | 월납·분기납·1회성 규칙 지원. D-3 예고 + D-1 확정 알림. 금액·기관·납부 수단 표기 |
| F5 | **웹 대시보드** | 주간 매트릭스(가로 날짜 × 세로 기관), 항목별 완료 체크, 원본 캡처 열람 |

### P1 — v1에 포함하되 단순하게

| ID | 기능 | 요구사항 |
|----|------|----------|
| F6 | **아이 대화 카드** | 행사 전날 리마인드에 대화 거리 1문장 포함("내일 ○○ 가지? 뭐가 기대돼?"), 행사 다음날 후속 질문 1문장. 대화 여부 체크(✅) |
| F7 | **월간 지출 뷰** | 매월 1일 "이번 달 나갈 교육비" 발송 + 대시보드 수납 캘린더 탭 (금액·날짜·기관·합계) |
| F8 | **주간 리포트** | 일요일 저녁: 이번 주 처리 건수 · 놓친 것 · 나를 위한 시간 넛지 1문장 |

### P2 — 넣고 싶었지만 뺀 것 (이번 범위 밖 · 만들지 않을 것)

| 뺀 것 | 넣고 싶었던 이유 | 뺀 이유 |
|-------|------------------|---------|
| 아이용 체크보드 | 아이가 스스로 챙기는 습관까지 만들고 싶었다 | v1은 "워킹맘의 생활을 돕는다"로 좁혀야 명확해짐 (사용자 결정) |
| 성장 시간 블록 예약·추적 | 되찾은 저녁을 '나를 위해' 쓰게 하고 싶었다 | 주간 리포트의 넛지 한 줄로 충분한지 먼저 검증 |
| 알림장 앱 자동 연동/크롤링 | 캡처조차 없애면 완전 자동이니까 | e알리미·밴드 등 크롤링은 법적·기술 리스크. 캡처 방식이 모든 채널을 커버 |
| 엄마들 단톡방 비공식 정보 | 실제 정보의 상당량이 여기서 온다 | 맥락·신뢰도 판단이 복잡 → 공식 공지 먼저 |
| 멀티테넌트 (다중 사용자) | 처음부터 서비스로 만들고 싶었다 | 본인 실사용으로 가치 검증이 먼저 (v3) |

## 7. 엣지 케이스 및 처리 원칙

| 상황 | 처리 원칙 |
|------|----------|
| 날짜가 애매한 공지 ("다음 주 중") | **지어내지 않는다.** 인박스에 보류(hold) 후 텔레그램으로 되물음 |
| 같은 공지 중복 투입 | 중복 감지 → "이미 담겨 있어요" 회신 (중복 리마인드 방지) |
| 기관 식별 실패 | "어느 기관 공지예요?" 1회 질문 → 답변을 학습해 이후 자동 인식 |
| 손글씨·저화질 캡처 | 읽은 만큼만 추출 + "이 부분은 못 읽었어요" 정직하게 표시 |
| 금액 오인식 리스크 | 수납 항목은 회신 메시지에 **금액·날짜를 반드시 표기**해 즉시 검증 가능하게 |
| 봇/서버 장애 | 파이프(적재)와 두뇌(추출) 분리 — 적재는 단순해서 죽을 일이 없게, 추출 실패 시 재시도 |

## 8. 기술 아키텍처 (Technical Architecture)

> 1~3주차 「관점노트 OS」에서 실배포로 검증한 스택을 재사용한다. **"파이프는 멍청하게, 두뇌는 분리"** 원칙 유지.

```
[텔레그램 봇] ─▶ [Vercel Webhook: 적재만 하는 멍청한 파이프] ─▶ [Supabase (Postgres + Storage)]
                                                                      │
        [Claude API (비전): 캡처·PDF → 항목 추출·분류] ◀──────────────┘
                                                                      │
        [리마인드 엔진 (Vercel Cron)] ─────────────────────────────────┤
          · 매일 저녁 브리핑  · 수납 D-3/D-1  · 매월 1일 지출 뷰  · 주간 리포트
                                                                      │
        [웹 대시보드 (Next.js, 비밀번호 보호)] ◀───────────────────────┘
```

| 구성요소 | 선택 | 근거 |
|----------|------|------|
| 입구 | Telegram Bot | 3주차에 검증 완료. 캡처 전송이 이미 습관 |
| 파이프 | Vercel Serverless Webhook | 적재만 담당 → 항상 켜져 있고 단순 |
| 추출 두뇌 | Claude API (비전 모델) | 이미지·PDF 혼합 입력 + 한국어 알림장 문맥 이해. **v1의 기술 핵심 검증 지점** |
| 저장 | Supabase | Postgres(항목) + Storage(원본 캡처 보관 — 출처 확인용) |
| 스케줄 | Vercel Cron | 3주차 밤 처리 루프에서 검증 완료 |
| 프런트 | Next.js on Vercel | 검증 완료. 모바일 반응형 필수 |

### 데이터 모델 (초안)

- `institutions` — 기관 (이름, 유형: 학교/학원, 별칭 학습)
- `items` — 항목 (기관ID, 유형 5종, 내용, 기한일, 반복규칙, 금액, 상태: 대기/완료/보류, 원본ID)
- `captures` — 원본 (이미지/PDF 경로, 수신시각, 추출결과 JSON)
- `payments` — 수납 규칙 (기관ID, 주기: 월납/분기납/1회, 기준일, 금액)
- `talks` — 대화 카드 (행사 항목ID, 전날/다음날 질문, 체크 여부)

## 9. 리스크와 대응 (Risks)

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 비전 추출 정확도가 낮으면 신뢰 붕괴 (잘못된 리마인드 > 리마인드 없음) | 높음 | 회신 메시지에 추출 결과를 항상 노출해 즉시 검증·수정 가능하게. 확신 낮으면 보류+질문 |
| 알림장에 개인정보(아이 이름·학교) 포함 | 중간 | 개인 전용 서비스로 비밀번호 보호, 원본은 비공개 Storage. v3 서비스화 시 별도 설계 |
| 리마인드 피로 (알림 과다) | 중간 | 노티는 하루 1회 브리핑으로 묶는 것이 기본. 수납 D-3/D-1만 예외 |
| 반복 규칙의 예외 (방학, 휴원) | 낮음 | "이번 주 쉬어" 자연어 명령으로 일시 중지 |

## 11. 검증할 가정 (유저 피드백 설계 — 과제 2 연결)

이 PRD가 서 있는 가정들. 유저 피드백은 "좋아요?"가 아니라 **이 가정 중 무엇이 깨지는지**를 확인하는 과정이다.

| # | 가정 | 깨졌다는 신호 (관찰할 것) |
|---|------|---------------------------|
| A1 | 캡처를 '설명 없이 던지기만' 하는 행위는 30초 이내라 습관이 된다 | 캡처를 모아뒀다 몰아서 던짐 / 며칠씩 안 던짐 |
| A2 | AI 추출 정확도는 신뢰를 유지할 수준이다 (잘못된 리마인드 < 리마인드 없음) | 회신 내용을 수정하는 빈도가 주 1건 초과 / 리마인드를 의심해 원본을 재확인 |
| A3 | 노티는 하루 1회 저녁 브리핑으로 충분하다 (더 많으면 피로) | 브리핑을 안 읽고 넘김 / 반대로 "아침에도 알려줘" 요청 |
| A4 | 행사 전날 '아이 대화 카드'는 실제로 쓰인다 | 대화 체크가 계속 빈 채로 남음 (기능이 아니라 죄책감 버튼이 됨) |
| A5 | 수납 D-3/D-1 이중 알림이 연체를 없앤다 | D-3는 무시되고 D-1만 유효 / 알림에도 연체 발생 |
| A6 | 다른 워킹맘도 같은 문제를 같은 강도로 겪는다 (v3 전제) | 피드백 인터뷰에서 "그냥 알림장 앱 알림 보면 되는데?" 반응 |

> 피드백 방법: 실제 워킹맘 2명 이상에게 캡처→브리핑 흐름을 직접 써보게 하고, **말보다 멈칫하는 순간**을 관찰. (+가상 페르소나 패널로 사전 검증)

## 13. 맘브레인 2.0 — 아이 케어 종합 OS 확장 비전

> v1 사용 중 확정된 방향 (2026-07-23): 알림장 리마인드를 넘어, **워킹맘이 아이를 케어하기 위한 물리적인 모든 것(일정·비용·성적·건강)을 기록하고, 필요한 시점에 리마인드하고, 아이와의 대화를 넛징하는 종합 서비스**로 확장한다.

### 13.1 구조 — 4개 기둥 + 1개 가로축

```
            [ 기억은 시스템이, 아이는 엄마가 ]
  📅 일정          💰 비용         📊 성적          🩺 건강/마음
  알림장·행사      수납·지출       레벨테스트·      신체 변화·건강 이슈
  캘린더 뷰 ✅     (v1 완성 ✅)    학교 성적표      (감기·장염 등)
                                  사진→과목별·     아이 고민·엄마 고민
                                  일자별·기관별    관계 기록
  ──────────────────────────────────────────────────────────
   💬 대화 넛지 (가로축) : 필요한 시점에 "오늘 저녁 한마디"
   행사 전날 · 시험 결과가 나온 날 · 아팠던 날 · 고민을 기록한 날
```

**설계 원칙 유지:** 입구는 그대로 하나(텔레그램 캡처). 성적표 사진도, "오늘 애 열나서 조퇴" 한 줄도 같은 봇에 던지면 두뇌가 유형을 판단해 각 기둥으로 분류한다.

### 13.2 신규 모듈 정의 (v2)

| 모듈 | 무엇을 | 입력 | 출력 |
|------|--------|------|------|
| **📊 성적 관리** | 과목별(영어·수학·국어·예체능) 레벨테스트 결과·학교 시험 성적 기록 | 성적표·결과지 사진 캡처 | 과목×일자×기관 정리 뷰, 추이 확인, 결과 나온 날 대화 넛지 ("시험 어땠어?"가 아니라 "어느 문제가 제일 재밌었어?") |
| **🩺 건강/마음 관리** | 신체 변화(키·몸무게), 건강 이슈(감기·장염·병원), 아이 고민, 엄마 고민, 관계 기록 | 텔레그램 한 줄 ("오늘 열 38도, 소아과 다녀옴") | 시간순 건강 타임라인, 병원 방문 기록, 회복기 대화 넛지, 고민 기록 후 관계 넛지 |
| **📅 네이버캘린더 내보내기** | 맘브레인 일정을 네이버캘린더에 등록 | — | 남편·가족과 일정 공유 |

### 13.3 네이버캘린더 연동 기술 검토 (2026-07-23 조사)

| 방식 | 판정 | 근거 |
|------|------|------|
| 공식 OpenAPI 일정 **쓰기**(`createSchedule`) | ✅ 채택 | 네이버 로그인(OAuth) 연동 필요. 맘브레인→네이버 단방향 내보내기 |
| 공식 API 일정 **읽기** | ❌ 불가 | 네이버는 조회 API를 공식 제공하지 않음 |
| CalDAV/iCal 양방향 | ⚠️ 보류 | 애플리케이션 비밀번호 방식, 비공식 활용이라 안정성 리스크 — "죽지 않는 파이프" 원칙 위배 |

### 13.4 구현 순서와 게이트

1. ✅ **캘린더 뷰** (v1.5, 완료) — 기존 데이터 재사용, 즉시 체감
2. **유저 피드백 게이트 (과제 2)** — 성적·건강 모듈은 **피드백 질문에 포함해 가정 검증 후** 착수: "성적·건강까지 한곳에서 관리된다면 쓰시겠어요?" (§11 가정 A6 확장)
3. 📊 성적 관리 → 🩺 건강/마음 → 📅 네이버 내보내기 순
